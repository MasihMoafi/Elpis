## Reported checkpoint conflict

Masih subsequently reported `Memory save failed: checkpoint changed during
consolidation`. Earlier app-server memory fixtures did not run the TUI's separate
end-of-turn checkpoint writer, so their success did not cover this interaction.
The saver holds `memory-save.lock` while consolidating; the terminal writer did
not acquire that lock. An asynchronous previous-turn mirror can therefore change
ES after the next saver reads it. The existing equality check correctly refuses
to overwrite that changed file.

The focused test invokes the actual TUI checkpoint writer while a saver snapshot
is alive, then attempts the save. The correction coordinates ES writers with a
workspace checkpoint lock, skips the redundant terminal mirror while the saver
owns ES, and gives the saver a bounded asynchronous wait if the short terminal
write acquired the lock first. A separate global lock still protects shared
MEMORY, so an unrelated workspace can keep writing its checkpoint. Manual edits
must still reject a stale save.

The separate before-fix test build was cancelled before executing tests; no
failing baseline run is claimed. Source inspection identified the uncoordinated
writers. Candidate checks cover both lock orderings, a different workspace, and
manual edits. The candidate's ten checkpoint tests passed, including the actual
TUI writer collision, reverse lock order, unrelated workspace, and manual edit
controls. The actual-widget animation test also passed: active colors change,
then remain static after turn completion even while another task stays busy.
Evidence: `checkpoint-candidate-tests.log` and `idle-animation-candidate-test.log`
under `.tmp/final-candidate/`. These are focused candidate checks, not user
acceptance. The new core-only lock test was not separately executed.
