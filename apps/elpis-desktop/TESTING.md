# Desktop verification

`test-inventory.json` owns every app test exactly once: **fast** (helpers and component contracts), **bridge**, **desktop** (main/preload contracts), **ui** (browser journeys), or **opt-in** (native/engine). The gate scans app sources, including legacy files importing `node:test`; unassigned, duplicate and missing files fail before any tests run. Add new tests to the inventory.

Run **`npm test`** for the complete ordinary gate: build bridge resources → fast → bridge → locked renderer build → desktop → every UI file, serially with a 180s limit per file. Resources are prepared before any selected tier; desktop and UI runs build the renderer once before their first test. This works without prebuilt resources or `out/`. Set `ELPIS_PLAYWRIGHT_PACKAGE` when Playwright is outside local dependencies and `ELPIS_CHROMIUM` for a system browser. Tier runs use a throwaway `ELPIS_HOME`. Existing dependencies are required; the gate never installs anything. `npm run test:inventory` checks ownership; `npm run test:fast`, `test:bridge`, `test:desktop`, and `test:ui` select a tier from the same inventory.

Each run prints `/tmp/elpis-test-gate-*/summary.json` and retains per-file TAP/build logs there. `wallMs` includes shared-lock waits and build time; `testMs` sums Node test durations and excludes those waits and the build. Compare like scopes: the architecture review measured bridge 4.77s (328), desktop plus selected helpers 3.06s (155), renderer 3.84s (1), and live-events 0.18s (13), **without a full UI gate measurement**. A focused browser test can use `flock /tmp/elpis-desktop-ui.lock node --test --test-timeout=180000 --test-reporter=tap tests/<file>` with output redirected to a TAP file.

Opt-ins stay explicit; never run the whole tier blindly. `ELPIS_TEST_ENGINE=/absolute/elpis-next node --test tests/composer-engine.test.mjs` uses an isolated engine without inference. Native window tests (`code-opens-electron`, `session-windows-electron`) require a private display: `ELPIS_PRIVATE_DISPLAY=1 xvfb-run -a flock /tmp/elpis-desktop-ui.lock node --test tests/<file>.test.cjs`. Other runtime scripts document their arguments and profile isolation in their headers; some make subscription turns. Keep `ELPIS_HOME` isolated and read the individual script before running it.

Bridge failure responses carry `code`, `requestId` (also `X-Request-Id`) and, when present, numeric `runtimeCode`. Existing error notices show the code and ID through `lib/api.ts`. HTTP 5xx diagnostics go to `<ELPIS_HOME>/logs/desktop-requests.jsonl` (0600): timestamp, ID, fixed method/area/cause categories, status and codes only. No bodies, headers, query strings, paths, error messages or stacks enter the log. Writes serialize per bridge; the file resets at 1 MiB (about 1 MiB plus one record maximum). If file logging fails, the same sanitized record goes to stderr. This deliberately limits forensic detail and retention; unknown-delivery messages keep their existing wording and no request is retried automatically.
